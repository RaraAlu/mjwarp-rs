# `f32::mul_add` 复测（QA 独立探针；非实现方数字）

环境：rustc 1.99.0 (b940084d7 2026-09-28)，x86_64-pc-windows-msvc，默认 target-feature（不含 fma）。
探针源码：`muladd_steps.rs`（`black_box` 阻止常量折叠）。
输入：被核单测同一组 cam1 四元数 `0x3f3d3c57 0x3f01dbed 0x3e805783 0x3ebb0653`（mujoco 序 w,x,y,z）。

## 1. 逐步对照（opt-level=0 与 opt-level=3 输出完全相同，见 §3）

| 步 | 精确单次舍入（QA Fraction 实现） | `f32::mul_add` 实测 |
| --- | --- | --- |
| `q11 = q1*q1` | `0x3e83bec4` | `0x3e83bec4` |
| `s1 = fma(q0,q0,q11)` | `0x3f4dc189` | `0x3f4dc189` |
| `s2 = fma(-q2,q2,s1)` | **`0x3f3daba1`** | **`0x3f3daba0`** |
| `s3 = fma(-q3,q3,s2)`（= e0） | `0x3f1b8312` | `0x3f1b8311` |

⇒ 本工具链上 `f32::mul_add` 在运行时**不是**单次正确舍入：单步就能差 1 ULP。

## 2. 常量折叠 vs 运行时（这是差异的真正来源）

实现方 `fma-toolchain-note.md` 的 `-O` 行给出「正确」值，是因为那条 `-O` 程序的操作数被编译器常量折叠
（精确求值），**不是** release 构建在运行时更正确。我把操作数全部 `black_box` 后：

- opt-level=0：`e0=0x3f1b8311`、`e2=0x3f3dbdb8`
- opt-level=3：`e0=0x3f1b8311`、`e2=0x3f3dbdb8`（与 opt0 逐位相同）

即 **profile 不是变量**；变的是「输入是否是编译期常量」。

## 3. 另一个 canonical 反例（说明不是「全局都错」）

`fma(a,b,c)`，`a=0x3f800001`（1+2^-23）、`b=0x3f7fffff`（1−2^-24）、`c=-1`：
精确值 = `2^-24 − 2^-47` → `0x337ffffe`；`mul_add` 实测 `0x337ffffe`（此例正确）。
⇒ 该实现并非整体偏移，而是个别情况下少一次正确舍入，所以**不能**用「加个补偿」绕，必须换成精确实现。

## 4. 对本片的支撑

生产代码用 `crate::math::fma::fma_f32`（`vfmadd231ss` 硬件主路 + 整数精确兜底）。我用 `_mm_fmadd_ss`
（同一指令）复算 1003 条参考四元数 × 9 元素 = 9027 项，与 pinned GPU 参考 **0 差异**（见 `hw-fma-9027.txt`）。
结论：改用 `fma_f32` 的决定成立；但 note 的**归因措辞**需按 §2 修正（观察 O3）。
