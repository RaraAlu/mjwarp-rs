# criterion v2.1 proposal (Arch; proposal only, no criterion/reference/value change)

Status: **PROPOSAL - not in force.** Nothing in this document is a criterion, nothing was
signed, and no criterion, reference, fixture, kernel or code value was changed to produce it.
It is written for Chief to take to the user. Executing it (step 3) starts only after the user
signs a new criterion version.

Context: under the signed `render-sdf-criterion-v2` (B = 128 ULP) the attempt4 freeze step
fails for two independent reasons, established by exact replay and recorded in
`outline-replay-findings.txt`:
1. the v2 section-2 predicate (4-neighbour outline band) covers only 9/183 (recipe) and
   18/172 (aa2) of the affected pixels, so the fail-closed rule rejects the rest;
2. the v2 section-3 freeze-time recomputation gives 512 ULP (and 2048/512 on the band sets),
   above the signed 128, and v2 forbids raising B.
This proposal addresses both without touching any numeric value.

## A. Exact difference set as the list (replaces the three-condition predicate)

Definition (per arm): `list(arm) = { p : depth_bits_form_A(p) != depth_bits_form_B(p) }` over
all camera-1 sphere pixels, where form A is the `a` association (0,1,2) (scene-a reference
form) and form B is (1,0,2) (product form after the a-order refix).

Measured (exact replay, reproduces attempt3 bit-for-bit):

| arm | sphere pixels | list size | first differing pixel | first xy | max observed ULP |
| --- | --- | --- | --- | --- | --- |
| recipe (spp=1) | 747 | **183** | 28969 | (169,120) | **73** |
| render_kernel_flags aa2 (spp=2) | 745 | **172** | 29448 | (168,122) | **91** |

Both first-differing pixels are exactly the attempt3 first-difference records
(`render_kernel_depth_seg` / `render_skybox_reference` / `render_e2e` / `render_kernel_rgb`:
28969 = (169,120); `render_kernel_flags` aa2 arm: 29448 = (168,122)).

Why "outside the list delta = 0" holds constructively: the list is not a geometric heuristic,
it is the complete difference set of the two association forms over every sphere pixel of the
frozen reference. The product after the refix computes form B; the reference is form A.
Therefore the product can differ from the reference only on pixels where the two forms differ,
i.e. exactly on `list(arm)` - every pixel outside it must compare bitwise equal. The window
verifier enforces this directly and fail-closed:
- outside the list: any non-zero delta (1 ULP included) fails;
- inside the list: `|delta| > B` fails;
- list membership itself must match pixel-for-pixel (an extra or missing pixel fails), so the
  tool cannot shrink or grow the list at compare time.

Freeze contract (proposed):
- one list file per arm: `scene-a-sphere-outline-<arm>.txt` (ASCII, LF) with a header
  (criterion version, reference path + sha256, camera/raster/spp, columns) and one row per
  listed pixel, sorted by pixel index:
  `pixel x y ref_seg_geom ref_seg_type ref_depth_bits formA_bits formB_bits ulp_ab`
  (the per-pixel bound column of section B is added by the step-3 tool update);
- the list file sha256 goes into the guards file and the window evidence, and both lists are
  part of the frozen 92-entry guard set; rewriting a list inside the window is a failure;
- the freeze-time tool re-derives the lists from the pinned fixtures and must reproduce these
  hashes; a mismatch fails before the body starts.

## B. Per-pixel strict bound (same formula as v2 section 3, evaluated per pixel)

For every pixel in the list, evaluate the v2 section-3 formula with that pixel's own inputs
(its `|c|`, its `a`, its `sqrt(det)`, its `depth`, its `ULP(depth)`). Two calibers are reported
and kept apart everywhere below:

```
bound_raw(px) = [ 5u * |c(px)| * |vz(px)| / (2 * a(px) * sqrt(det(px))) ] / ULP(depth(px))
margin(px)    = 1.15 * bound_raw(px)          (the x1.15 margin required by v2 section 3)
```

Bound distribution over the list pixels (both calibers; ratios state which caliber they use):

| arm | bound_raw min / median / max (pixel) | margin min / median / max (pixel) |
| --- | --- | --- |
| recipe | 25.39 / 32.13 / **360.49** (29216) | 29.20 / 36.95 / **414.57** (29216) |
| aa2 | 25.35 / 32.40 / **430.02** (32587) | 29.16 / 37.26 / **494.52** (32587) |

Observed deltas against each caliber (max observed recipe 73, aa2 91):

| arm | observed max | max observed / bound_raw | max observed / margin | median observed / bound_raw | median observed / margin | pixels with ratio >= 1 |
| --- | --- | --- | --- | --- | --- | --- |
| recipe | 73 | **0.4005** (30409: 13/32.46) | **0.3483** (30409: 13/37.33) | 0.1939 | 0.1686 | **0** (both calibers) |
| aa2 | 91 | **0.4203** (29687: 19/45.20) | **0.3655** (29687: 19/51.98) | 0.1951 | 0.1696 | **0** (both calibers) |

Interpretation: the error model holds (no pixel exceeds its own bound under either caliber), but
the analytic bound is **loose**: the worst observed delta is 0.40x / 0.42x of `bound_raw`, i.e.
0.35x / 0.37x of `margin`; equivalently the bound is 2.50x / 2.38x the observed worst case under
`bound_raw` and 2.87x / 2.74x under `margin`. The loose factor comes from the model constants
(delta-a <= 4u*a, 5u*|c| and a ~= 1), not from the data.

Old "independent extremes multiplied" caliber, as a contrast:

| arm / set | sqrt(det)_min | |c|max | |vz|max | raw bound | x1.15 -> pow2 |
| --- | --- | --- | --- | --- | --- |
| recipe / band4 (90 px) | 2.199769e-03 | 1.894825 | 0.974813 | 1049.60 | 2048 |
| recipe / derived affected (183 px) | 6.356325e-03 | 1.894825 | 0.974192 | 363.01 | 512 |
| aa2 / band4 (89 px) | 5.233964e-03 | 1.894825 | 0.974513 | 441.00 | 512 |
| aa2 / derived affected (172 px) | 5.233964e-03 | 1.894825 | 0.973897 | 440.72 | 512 |

Honest note on that contrast: on the exact-difference set the independent-extremes value and
the per-pixel maximum almost coincide (363.01 vs 360.49 recipe; 440.72 vs 430.02 aa2, both
`bound_raw`), so the "extremes come from different pixels and the product is unreachable"
effect is NOT the main gap here. The 2048 figure comes from the old band4 predicate dragging in
a pixel that is not in the difference set: recipe band4's minimum sqrt(det) belongs to pixel
**28973** (sqrt(det) 0.002200) while the difference set's minimum is 0.006356 (pixel 29216);
for aa2 the band4 minimum-sqrt(det) pixel 32587 already lies inside the difference set, which is
why aa2 stays at 441.00 -> 512. The real gap between the recomputed bound and the observed
deltas is the analytic-model looseness quantified above (2.87x / 2.74x under `margin`).

## C. Candidate B values (both listed; no value changed)

### C1. B_rigorous = 512 ULP
`B_rigorous = next power of two >= max(bound(px) * 1.15)` = 512 ULP (both arms; recipe max
414.57, aa2 max 494.52).
- Basis: strict per-pixel application of the signed v2 section-3 formula; every listed pixel
  is then covered by the derived bound, so the criterion stays "derive-guaranteed".
- Risk / cost: 512 is 5.6x the observed worst case (91 ULP). The criterion would formally
  admit deltas far beyond anything observed, and the numeric jump from the signed 128 is
  large, so it needs an explicit signature and a written rationale.
- Note (margin caliber): only 4 pixels per arm have a per-pixel margin above 128 - recipe
  pixels 28969/28970/29215/29216 (max 414.57 at 29216, observed there 73), aa2 pixels
  29457/32587/33307/36896 (max 494.52 at 32587, observed there 91); under the bound_raw
  caliber it is 1/3 pixels (recipe 29216; aa2 32587/33307/36896). So the 512 is driven by a
  handful of near-tangent pixels.

### C2. B_empirical = 128 ULP (unchanged from the signed v2)
- Basis: observed maximum on the frozen lists is 73 ULP (recipe) and 91 ULP (aa2), i.e. a
  1.41x margin over 91; it also keeps the signed value and requires no numeric change.
- Risk / cost: 128 is NOT supported by the strict per-pixel bound - 4 pixels per arm have a
  margin above 128 (raw caliber: 1/3), so under the strict error model the criterion could
  admit a pixel that then exceeds B, and the "fail-closed by derivation" property is weakened
  to "fail-closed by observed calibration". If the reference or the frozen ray grid ever
  change, the 1.41x margin is not protected by the model.
- This is the value currently signed; listing it does not change it.

The two candidates differ only in the numeric limit; changing the list predicate (section A) is
the essential fix and is required by either candidate. Section D states the option Chief
intends to take to the user (B stays 128, but the derivation becomes exactly computable).

## D. Exact-computable B (the configuration to be taken to the user; B stays 128)

This section is the recommended reading of the same numbers; it changes no value that is
already signed (B = 128 ULP stays 128) and it does not touch spec, tool or guards before the
user signs.

Premise (replay fidelity; acceptance-audit "A-class + explicit premise"): the exact values are
the output of a host-side f32 replay that has been checked bitwise against the frozen data:
camera rays 256/256 against the S5 fixture samples; form A reproduces the frozen reference depth
bits on every camera-1 sphere pixel (747/747 recipe, 745/745 aa2); form B vs form A gives 183 px
/ 73 ULP (recipe) and 172 px / 91 ULP (aa2), exactly the attempt3 observations. The premise is
"same frozen reference forms + same frozen product kernel identity (source 10070226.. / PTX
7782aeb1.. / 268,589) + freeze-time re-derivation"; if any of those do not hold the numbers are
not applicable, and the freeze step fails closed instead of reinterpreting them.

The difference between the two association forms is not only bounded, it is **exactly
computable**: the replay returns the exact f32 depth bits of form A and form B for every pixel,
so the exact per-pixel difference of the frozen product shape versus the frozen reference is
available at freeze time. Measured on the frozen lists:

| arm | list pixels | exact max |delta| | B = next power of two >= exact max |
| --- | --- | --- | --- |
| recipe (spp=1) | 183 | **73 ULP** | **128** |
| render_kernel_flags aa2 (spp=2) | 172 | **91 ULP** | **128** |

So with the exact-difference list of section A, B = 128 ULP is simply "the next power of two
above the exact maximum difference" (91 -> 128); it is derived, not observed-then-rounded.

Why the analytic bound is not used to set B: the v2 section-3 analytic expression gives, per
pixel, 414.57 ULP (recipe) and 494.52 ULP (aa2) after the x1.15 margin (raw max 360.49 / 430.02)
- i.e. 5.68x / 5.43x the exact maximum (raw 4.94x / 4.73x). For a quantity that can be computed
exactly, using a loose analytic upper bound would inflate B by roughly 4.7-5.7x (more than the
3-4x rough estimate) purely out of over-conservatism; that is a modelling preference, not a
safety requirement. The analytic bounds are kept in this proposal and in the evidence as
**recorded loose upper bounds only**, explicitly not used to determine B.

Freeze-time rule (fail-closed, same spirit as the signed v2):
- the freeze-step tool re-derives the lists from the pinned fixtures and recomputes the exact
  per-pixel max difference with the frozen product kernel shape;
- the two list sha256 values and the exact maximum differences are written into the guards file;
- if the recomputed exact maximum difference exceeds 128 ULP, the attempt FAILS at the freeze
  step - no raising B, no re-freeze in the same attempt;
- if the list membership or a list sha256 differs from the frozen values, the attempt FAILS;
- a list pixel above 128 ULP, or any pixel outside the list with a non-zero delta, FAILS.

Boundary and cost (stated plainly, not as a routine pass):
- the exemption covers the **minimal pixel set that provably differs** (183 recipe / 172 aa2,
  camera 1 only; camera 0 = 0) at its exact, replay-computed values; every pixel outside the
  list keeps the bitwise requirement (0 ULP) unchanged;
- it is a documented, exact, fail-closed exemption, i.e. a deliberate relaxation of the
  bitwise depth requirement on those pixels, so it still needs the user's signature; it must
  not be described as a "normal threshold pass" or as "SDF verified";
- the exact numbers are only valid for the frozen reference forms and the frozen product kernel
  identity; the freeze step re-derives them and any drift fails closed.

## E. What step 3 would change after the user signs (not done now)

1. New criterion version (e.g. `render-sdf-criterion-v2.1`): section 2 becomes the exact
   difference set of section A, section 3 becomes the exact-computable B definition of
   section D (B = 128, next power of two above the freeze-time exact maximum difference,
   fail-closed), with the analytic per-pixel bound of section B recorded as a loose upper
   bound only; spec, receipt and signing block updated.
2. Authoring tool contract: emit the list files in the section-A format only (affected pixels)
   plus a per-pixel bound column and the distribution statistics; same pinned-environment,
   fail-closed, offline, zero-GPU wrapper, same two-run determinism and sha verification.
3. Window material: guards carry the two list sha256 values; preparation checklist gains
   "list hashes match the freeze-time re-derivation"; the freeze step fails if a hash differs.
4. Then the normal window path (fresh freeze -> guards-only -> body -> post-window recheck ->
   evidence commit -> QA review). Separate check still required: the pre-window baseline is
   re-sampled at window time and must be >= the signed floor (5328 MiB); the current desktop
   graphics load (util 93%) must also clear the regular monitor threshold.
