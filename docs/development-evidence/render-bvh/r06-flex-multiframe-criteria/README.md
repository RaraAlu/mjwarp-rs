## 1. 一句话结论

R06 目前只有**单帧**位级证据（closure `2026-11-04-render-r06-flex-closeout` / 证据 `1de0321a`；attempt6 `7a48205d`）；
「相邻时钟步位姿变化 → 渲染随之变化」**无判据、无参考、无实体**。
本草案给出**推荐方案 B**：帧内沿用已签单帧口径 + **跨帧变化可见性断言** + 产品=参考逐帧位级，共 **3 帧**、**1 个采集窗 + 1 个验证窗**。
**是否要做、帧数与阈值属用户决策**；本卡不代签、不实现、不采集。

## 2. 现状与缺口（写死）

- 单帧证据面：同一 GPU / 同一 recipe（`use_fast_math=false`）/ 同一编译形态下，对 `fixtures/render-bvh/scene-flex/reference/base/` 的 rgb ≤1 LSB（beyond_1_lsb=0）、depth ≤4 ULP（beyond4=0）、seg 精确相等、两跑 sha 相同。
- 唯一放宽：用户签名 allowlist `3406f1ca`，**仅** `cam2 / (x=134,y=128) / flexid0`、`ULP≤4 且 beyond4=0`，**仅对 base 帧参考生效**。
- 缺口：没有第二/第三帧参考；没有「位姿变了、渲染该跟着变」的判据；测试实体只有单帧用例（`render_flex_validate`）。

## 3. 三个候选方案

| 方案 | 做法 | 成本 | 判别力 | 结论 |
| --- | --- | --- | --- | --- |
| A 强 | 每帧都做独立位级参考（等价于把单帧判据重复 N 次） | 采集/体积最高（每帧 +4.73 MB，N 帧）；窗口不变但夹具线性增长 | 最强（每帧位级） | 可行但重，N≥5 时夹具明显变大，不建议作为首版 |
| **B 中（推荐）** | **帧内**沿用单帧位级判据；**跨帧**加「变化可见性」断言（相邻帧该相机 depth/seg 变化像素数 ≥ 阈值）+ 产品与参考逐帧位级相等 + 两跑 sha | 3 帧 ≈ 14 MB，1 采集窗 + 1 验证窗 | 足以证明「单帧正确 + 帧间变化被正确反映」 | **推荐** |
| C 弱 | 只判方向/单调性（位姿变 → 输出变），不做数值对照 | 最低 | 弱（不能证明数值正确） | 不建议作为验收判据，可作负控制 |

## 4. 推荐方案 B 的可判口径（细则）

**4.1 帧集**：3 帧 = `base` + 2 个时钟步（flex 位姿单调演化，例如沿某顶点方向逐步位移）。
帧集必须**有判别力**：参考帧之间要有可测变化（见 4.4 退化保护）。

**4.2 帧内判据（沿用已签，不重议）**：
- rgb：≤1 LSB 且 `beyond_1_lsb=0`；
- depth：≤4 ULP 且 `beyond4=0`；
- seg：精确相等；
- 两跑 sha256 相同。

**4.3 跨帧判据（新增，需用户签）**：
- 对指定相机：相邻帧 depth 或 seg 的**变化像素数 ≥ 阈值**（候选值：该相机像素数的 **0.5%**，**待用户签**）——证明「变化真的发生在渲染里」而不是静态假绿；
- 产品输出与参考在**每一帧**都位级相等（同 4.2）；
- 帧间判据用**整序列**：任帧失败即整轮失败。

**4.4 退化保护**：
- 采集后先算参考帧间差异；若相邻参考帧位级完全相同 → 该帧集判「无判别力」，**拒绝通过**（不是通过）；
- 变化像素数阈值必须低于实际参考变化量（留余量），避免阈值刚好卡在边界。

**4.5 失败条件（写死）**：任帧位级超界 / 变化像素数不足 / 两跑 sha 不同 / 参考帧无判别力 → 整轮失败；失败即停、不重试、不放宽。

**4.6 allowlist 不继承（写死）**：`3406f1ca` 只对 base 帧生效；新帧一律 bit-first。若新帧复现同一像素差，**必须报用户**，不得自动扩范围。

## 5. 采集方案（只写方案，不执行）

- **环境**：离线 authoring（pinned venv / editable mujoco-warp `71da24d9`；`use_fast_math=false`；同一 GPU）。禁止 PyPI 轮子（R06 S0 已留坑）。
- **脚本扩展点**：`scripts/authoring/capture_render_flex.py` 增加帧循环——步进 flex 状态（步数固定、可复现）→ 每帧记录 `flexvert_xpos`（host `state.npz`）+ 上游渲染参考（rgb/depth/seg）+ 相机位姿。
- **产物布局**：
  ```
  fixtures/render-bvh/scene-flex/multiframe/
    frame-000/{rgb.npz, depth.npz, seg.npz, state.npz}
    frame-001/{...}
    frame-002/{...}
    capture.json      # 帧数、步进参数、recipe、pin、provenance
    cam-poses.json    # 三相机位姿（同 base 口径）
    README.md         # 生成命令与 provenance
  ```
- **体积估算**：单帧 rgb 2.36 MB + depth 0.79 MB + seg 1.58 MB ≈ **4.73 MB/帧** → 3 帧 ≈ **14 MB**（npz 压缩后可能略小）。
- **确定性**：采集两次逐位相同（与既有 S0b/S3b 采集同纪律）；provenance 记 pin/recipe/GPU/时间。

| 项 | 影响 |
| --- | --- |
| `src/` | **零改动**（多帧不需要改渲染器） |

| 成本 | 2 片（采集 authoring + 实体/验证）+ **1 采集窗 + 1 验证窗**；无性能/AA 扩展 |

## 7. 风险

1. **阈值主观性**：0.5% 变化像素是候选值，需实测参考帧间差异后定；定太高会假失败、太低会假绿。
2. **场景判别力**：`scene-flex` 的 flex 位姿在当前时钟步下变化幅度可能很小（需先在采集时验证，否则整片无判别力）。
3. **允许清单边界**：若新帧复现 base 那 1 px 差异，需用户裁，不能自动继承。
4. **夹具体积**：3 帧 ≈14 MB；若用户要更多帧（如 5–10 帧），体积线性增长，需说明取舍。
5. **窗口与重冻**：新实体使当前 16 条 guards 失效，需重冻 + 一次验证窗；这期间渲染线不再有「已验证 exe 可直接复用」的状态。
6. **不做也能成立**：现有口径（单帧成立 / 多帧未覆盖）可以继续维持；本草案不构成必须做的理由。

## 8. 给用户的决策点

1. 要不要做多帧判据？（不做也能维持当前单帧口径）
2. 若做：帧数（推荐 3）+ 变化像素数阈值（候选 0.5%）+ 是否接受 ≈14 MB 夹具与 2 个窗口成本；
3. 若新帧复现 base 的 1 px 差异，如何处置（保持 bit-first 报红 / 逐帧单独签 allowlist）。
