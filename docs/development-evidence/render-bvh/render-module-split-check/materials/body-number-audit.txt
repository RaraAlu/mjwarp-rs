# body 数字审计：render.md（旧）vs render/index.md（新）

复核对象：`2026-10-30-render-module-split` 步 1
提交点：旧 = `9e1567a2`，新 = `7de14d30`
方法：全部在 git blob 字节上做（`git cat-file --batch`），不读工作区，不受 autocrlf 影响。
「body」定义：模块 md 里**最后一个 `+++` 行之后**的全部字节（含该 `+++` 行自身的行尾之后的空行）。

## 1. 实测

| 项 | 旧 `render.md` | 新 `render/index.md` |
| --- | --- | --- |
| 文件字节 | 9 119 | 3 923 |
| 行数（splitlines） | 393 | 201 |
| `+++` 行号 | 1 与 **369** | 1 与 **177** |
| body 行数 | 24 | 24 |
| body 字节（UTF-8） | **749** | **749** |
| body 字符数 | **421** | **421** |
| body sha256 | `f680bfbe2a589b81a68ca3368b45c07d268aa3fcf78f4f90985e45a32d29b730` | `f680bfbe2a589b81a68ca3368b45c07d268aa3fcf78f4f90985e45a32d29b730` |
| 文件末尾 | LF | LF |

⇒ **两份 body 逐字节相同**（含旧文件本来就以 LF 结尾）。

## 2. 证据里登记的值 vs 实测

`README.md §4` 与 `receipt.json:measured_lines` 登记：

| 登记项 | 登记值 | 实测 | 结论 |
| --- | --- | --- | --- |
| 旧 body 字节 | 421 | 749 | 不符（421 是**字符数**） |
| 新 body 字节 | 422 | 749 | 不符 |
| 旧 body sha256 | `4f54ed56…91f22` | `f680bfbe…9b730` | 不符 |
| 新 body sha256 | `483d91ae…de6df` | `f680bfbe…9b730` | 不符 |
| body 差异 | 「新文件末尾补 1 个 LF（421→422）」 | 两份 body 逐字节相同 | 不符（旧文件末尾本来就有 LF） |

我尝试过的候选口径（均不能复现登记的 sha256）：原始 body、去尾 LF、CRLF、去首个空行、去空行、UTF-16LE、GBK 重编码；
`421` 只能由 **str 字符数** 解释（749 B / 164 个 CJK 字符）。
⇒ 登记的 sha256 无法从任何合理编码的 body 复现（建议 Arch 用 `sha256(body_bytes)` 重测后改正）。

## 3. 结论

- **实质结论成立且比登记更强**：正文逐字保留 = **逐字节相同**（不是「末尾 +1 LF」）；行数口径 393/369/24 与 201/177/24 与登记一致。
- **需要修正的只是证据数字**（README §4/偏差 3 与 receipt.measured_lines）：不影响结构/迁移/validate 结论，也不需重跑任何门禁。
